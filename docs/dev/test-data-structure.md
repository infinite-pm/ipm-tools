# Test Data Structure

## Overview

All test data is organized based on the `tests/sources.json` configuration file, which drives both manual test generation tools and automated test suites.

## Directory Organization

Destinations in `sources.json`: `ipmt/ipmt-spec`, `ipmt/files-md`,
`ipmt/files-ipmt`, `ipmt/invalid`, `solver`, `layout-gen`, `layout-gen-ext`, and
the rule corpora `layout-gen-rules` / `layout-gen-ext-rules` (`.dsl` pins).

### `tests/ipmt/ipmt-spec/`
Canonical specification examples extracted from [`docs/ipmt-spec.md`](../ipmt-spec.md). These test cases validate the core ipmt language features and serve as the reference implementation of the specification.

**Purpose**: Verify parser compliance with the canonical ipmt specification

**Source**: `docs/ipmt-spec.md` code blocks

### `tests/ipmt/files-md/`
Examples extracted from various markdown documentation files across the repository. These include practical use cases, edge cases, and examples from design documents.

**Purpose**: Ensure documentation examples remain valid and up-to-date

**Source**: every markdown file in the repo except `tests/**` and `temp/**` (glob `../**/*.md`)

### `tests/ipmt/files-ipmt/`
Standalone `.ipmt` files (not extracted from markdown) parsed via the `ipmt-file` parser, e.g. `deploy-incident`, `murder-simple`, `two-containers`.

**Purpose**: Cover full standalone ipmt documents that live as their own files

**Source**: Standalone `.ipmt` files anywhere in the repo outside `tests/` and `temp/` (today `examples/*.ipmt`), via `sources_glob` with parser `ipmt-file`

### `tests/ipmt/invalid/`
Invalid test cases that should produce parse errors. These validate error handling, error messages, and ensure the parser correctly rejects malformed input.

**Purpose**: Verify parser error detection and reporting

**Source**: ` ```ipmt-invalid ` fences in `docs/ipmt-spec.md`

**Note**: Extracted by the dedicated `ipmt-invalid-md` parser in `sources.json`;
the case source is stored as `.ipmt-invalid`, and the pinned output is a
rejection sidecar — `.parser.error.json`, or `.validate.error.json` when the case
parses but `ipm-validate` rejects it (both generated by `make gen-invalid-sidecars`)

### `tests/layout-gen/`
Layout algorithm test cases focusing on specific layout scenarios like node positioning, edge routing, and algorithmic behavior.

**Purpose**: Validate layout generation algorithms

**Source**: `docs/dev/layout-gen/layout-alg.md` (and `layout-alg-ext.md` → `tests/layout-gen-ext/`, `layout-alg-shells.md` → `tests/layout-gen-shells/`, run with `--shells`)

## File Naming Conventions

For each test case with base name `example-name`, the following files may exist:

### Input Files
- **`example-name.ipmt`** - Source ipmt text file (valid lanes)
- **`example-name.ipmt-invalid`** - Source of a deliberate negative example
  (`tests/ipmt/invalid/` only)

### Generated Output Files
- **`example-name.json`** - Parser output (IpmGraph JSON)
- **`example-name.layout.json`** - Layout generation output
- **`example-name.ipm.svg`** - Visual diagram (static SVG)
- **`example-name.md`** - Per-case markdown page (written by `gen-test-md`)
- **`_refs.json`** (per directory) - case index plus `source_sha1` / `content_sha1`
  and the `outputs` hash map used by `--check` / `refs-rehash`

### Error Files (for invalid cases)
- **`example-name.parser.error.json`** - Pinned parser error details
- **`example-name.validate.error.json`** - Pinned validator findings (cases that
  parse but fail validation, e.g. `self-loop`)

## Test Case Metadata

Each test case is registered in `tests/sources.json` with the following structure:

```json
{
  "name": "example-name",
  "destination": "ipmt/ipmt-spec",
  "source_files": ["../docs/ipmt-spec.md"],
  "method": "parser",
  "params": {
    "parser_name": "ipmt-md",
    "parser_params": {
      "filter": "valid"
    }
  }
}
```

### Key Fields

- **`name`** - Label for this sources.json ENTRY (a source group, e.g. "ipmt specification"); stored in `_refs.json`. Per-case base names are derived from the source heading/anchor or file name and de-collided automatically
- **`destination`** - Target directory for generated files (relative to `tests/`)
- **`source_files`** - Source markdown files to extract from (array of paths)
- **`sources_glob`** - Alternative: glob pattern for multiple sources
- **`method`** - Extraction method: `"parser"` or `"ignore"` (a legacy `"content"` mode also exists)
- **`params`** - Parameters for the extraction method:
  - **`parser_name`** - Parser to use (see the list below)
  - **`parser_params`** - Parser-specific parameters:
    - **`filter`** - For `ipmt-md`: `"valid"` (the default). Negative examples
      are not a filter — they use the dedicated `ipmt-invalid-*` parsers.

### Available Parsers

- **`ipmt-md`** - Extract ` ```ipmt ` code blocks from markdown files
- **`ipmt-invalid-md`** - Extract ` ```ipmt-invalid ` negative examples from markdown files
- **`ipmt-file`** - Process standalone `.ipmt` files
- **`ipmt-invalid-file`** - Process standalone `.ipmt-invalid` files
- **`ipmt-solver-md`** - Extract solver round-trip examples from markdown files
- **`ipmdev-layout-rule-md`** - Extract layout test rules from markdown files

### Examples

**Extract valid IPMT cases from specification:**
```json
{
  "name": "ipmt specification",
  "destination": "ipmt/ipmt-spec",
  "source_files": ["../docs/ipmt-spec.md"],
  "method": "parser",
  "params": {
    "parser_name": "ipmt-md",
    "parser_params": {
      "filter": "valid"
    }
  }
}
```

**Extract invalid IPMT cases:**
```json
{
  "name": "ipmt specification - invalid cases",
  "destination": "ipmt/invalid",
  "source_files": ["../docs/ipmt-spec.md"],
  "method": "parser",
  "params": {
    "parser_name": "ipmt-invalid-md"
  }
}
```

**Process all markdown files with glob:**
```json
{
  "name": "ipmt examples in documentation",
  "destination": "ipmt/files-md",
  "sources_glob": ["../**/*.md"],
  "method": "parser",
  "params": {
    "parser_name": "ipmt-md",
    "parser_params": {
      "filter": "valid"
    }
  }
}
```

**Ignore test and temp directories:**
```json
{
  "name": "skip temp and tests directories",
  "destination": "",
  "sources_glob": ["../tests/**", "../temp/**"],
  "method": "ignore"
}
```

## Generation Workflow

### 1. Add the source example
Add the example as a ` ```ipmt ` / ` ```ipmt-invalid ` fence in a source doc, or as
a `.ipmt` file outside `tests/` (e.g. `examples/`).

### 2. Extract fixtures
Extract the fixture TEXT (`.ipmt` / `.ipmt-invalid` / `.dsl`) and refresh `_refs.json`. This step does NOT parse — the `.json` graph goldens are produced separately with `cmd/ipmt-parse` and only COMPARED by `TestParseValidCases`:
```bash
go run ./cmd-dev/sync-test-cases --rm-extra   # extract fixture text per tests/sources.json
# goldens for a case (when its parse output changed intentionally):
go run ./cmd/ipmt-parse --in tests/<lane>/<case>.ipmt > tests/<lane>/<case>.json
```

### 3. Generate Layout
Create layout positioning from parser output:
```bash
go run ./cmd/layout-gen --in tests/<lane>/<case>.ipmt --out tests/<lane>/<case>.layout.json
# the layout corpora are regenerated wholesale by `make layout-test`
```

### 4. Generate Diagrams
Render static `.ipm.svg` diagrams from the layout JSON with `ipmsvg-gen`.

### 5. All-in-One
The order matters — `_refs.json` output hashes only settle at the end:
```bash
make sync-test-cases      # fixture text + _refs.json
make gen-invalid-sidecars # invalid-lane rejection sidecars
make layout-test          # rewrites the corpora .layout.json
make gen-test-md          # per-case .md
make refs-rehash          # refresh the _refs.json output hashes
go run ./cmd-dev/sync-test-cases --check   # must exit 0
```

## Verification

### Check Coverage
Verify extracted fixtures and `_refs.json` are in sync (prints `DIFF refs:` /
`EXTRA file:` and exits 1); it does NOT assert that every case has a complete
output set:
```bash
go run ./cmd-dev/sync-test-cases --check
```

### Run Automated Tests
Validate all test cases:
```bash
go test ./pkg/ipm/parser -v
go test ./pkg/layout -v
```

## Adding New Test Cases

### 1. Add the source example
Fixtures are GENERATED — never hand-create files under `tests/` (that tree is in the
ignore list, and a source inside a destination dir is a fail-fast error). Add your
example as a ` ```ipmt ` fence in a doc that is already a source, or as a `.ipmt`
file outside `tests/` (e.g. `examples/`).

### 2. Register in sources.json
Add entry to `tests/sources.json`:
```json
{
  "name": "my-new-test",
  "destination": "ipmt/ipmt-spec",
  "source_files": ["../tests/ipmt/ipmt-spec/my-new-test.ipmt"],
  "method": "parser",
  "params": {
    "parser_name": "ipmt-file",
    "parser_params": {}
  }
}
```

### 3. Generate Outputs
```bash
make sync-test-cases && make gen-test-md
```

### 4. Verify
```bash
go test ./pkg/ipm/parser -run 'TestParseValidCases/ipmt/ipmt-spec/my-new-test' -v
```

## Test Documentation

### Generate Test Documentation
Create comprehensive test documentation with diagrams:
```bash
go run ./cmd-dev/gen-test-doc
```

Output: one markdown file per test destination under `temp/test-docs/` (e.g. `ipmt.md`, `layout-gen.md`, ...), plus a `README.md` index.

This includes:
- Table of contents by source
- Links to all test files
- Embedded ipmt source code
- Rendered diagrams

## Best Practices

1. **Descriptive Names**: Use clear, descriptive test case names that indicate what is being tested
2. **Organized by Purpose**: Group related tests in appropriate directories
3. **Document Intent**: Put explanatory comments in the SOURCE fence/file — the extracted `.ipmt` files are regenerated
4. **Keep Sources.json Updated**: Always register new test cases in `sources.json`
5. **Regenerate Regularly**: Run `make sync-test-cases && make gen-test-md` after parser changes
6. **Verify Coverage**: Run `sync-test-cases --check` (plus `refs-rehash --check`, `gen-invalid-sidecars -check`)
7. **Commit All Files**: Include both `.ipmt` source and generated outputs in version control
